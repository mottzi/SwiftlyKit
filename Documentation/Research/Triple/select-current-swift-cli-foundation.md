# Select the current Swift CLI foundation

**Researched:** 2026-07-26
**Decision:** Adopt Swift Argument Parser 1.8.2 as TripleCLI's only new package dependency. Use Swift concurrency and `AsyncStream`/`AsyncThrowingStream`, Foundation, Darwin, and OSLog for execution, output, terminal detection, JSON, and diagnostic telemetry.

## Recommended stack

| Concern | Selection | Decision basis |
| --- | --- | --- |
| Argument parsing, help, validation, exit codes | `swift-argument-parser` 1.8.2, in the `TripleCLI` executable target only | 1.8.2 is the current release; the package declares Swift tools 6.0, has no package dependencies, and describes its 1.x API as source-stable. It is compatible with Triple's Swift 6.3 baseline without adding a transitive dependency graph. [Release](https://github.com/apple/swift-argument-parser/releases/tag/1.8.2) · [Package manifest](https://github.com/apple/swift-argument-parser/blob/1.8.2/Package.swift) · [project status](https://github.com/apple/swift-argument-parser/blob/1.8.2/README.md#project-status) |
| Async command entry point | `AsyncParsableCommand` plus Swift structured concurrency | Argument Parser directly supports an async root and async `run()` methods. TripleCore already exposes operation and process events as standard-library async streams, so the CLI can consume those without an async helper package. [Async command guide](https://github.com/apple/swift-argument-parser/blob/1.8.2/Sources/ArgumentParser/Documentation.docc/Extensions/AsyncParsableCommand.md) · [Swift `AsyncStream`](https://developer.apple.com/documentation/swift/asyncstream) · [TripleCore operation snapshots](../../../TripleCore/Sources/TripleCore/Operations/OperationCoordination/OperationCoordinator/OperationCoordinator+Observation.swift) · [TripleCore process events](../../../TripleCore/Sources/TripleCore/Operations/ProcessExecution/ProcessSession.swift) |
| Shell completions | Argument Parser's generated Bash, Zsh, and Fish scripts | Every Argument Parser command receives `--generate-completion-script`; no completion package or handwritten shell model is required. Script installation should remain an explicit user action separate from enabling the `triple` executable. [Completion guide](https://github.com/apple/swift-argument-parser/blob/1.8.2/Sources/ArgumentParser/Documentation.docc/Articles/InstallingCompletionScripts.md) |
| Terminal detection | `FileHandle.standardOutput` / `.standardError` file descriptors plus Darwin `isatty` | `FileHandle` exposes the standard streams and their POSIX descriptors, while `isatty` answers whether a given descriptor is a terminal. Detect each stream independently; stderr being a TTY is the relevant gate for transient progress. This detects a terminal, not color support, so the first CLI should stay line-oriented and color-free. [FileHandle](https://developer.apple.com/documentation/foundation/filehandle) · [`isatty(3)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/isatty.3.html) |
| Progress and user-visible logs | A small TripleCLI-owned output router over `FileHandle` | Send command results to stdout and progress, streamed build output, warnings, and human errors to stderr. Use transient progress only when stderr is a TTY; otherwise emit ordinary newline-delimited phases. `FileHandle` is the SDK wrapper around descriptors and exposes both standard streams, so a spinner/progress dependency is not justified. [FileHandle standard-stream API](https://developer.apple.com/documentation/foundation/filehandle?changes=latest_major) |
| Internal diagnostics | Apple's `Logger` (`OSLog`), never as the CLI output contract | `Logger` writes severity-classified telemetry to unified logging for Console and the `log` tool. That makes it appropriate for debugging Triple itself, but distinct from stdout/stderr meant for people and automation. [Apple logging overview](https://developer.apple.com/documentation/os/logging) · [`Logger`](https://developer.apple.com/documentation/os/logger) |
| JSON | Explicit `Codable` response DTOs encoded with Foundation `JSONEncoder` | `Codable` is Swift's encoding/decoding protocol composition and `JSONEncoder` produces JSON data with configurable formatting. Emit exactly one versioned response document plus a trailing newline on stdout; keep progress and human prose off stdout in `--json` mode. Do not encode persistence/domain models directly, because that would accidentally make internal model changes part of the CLI contract. [`Codable`](https://developer.apple.com/documentation/swift/codable) · [`JSONEncoder`](https://developer.apple.com/documentation/foundation/jsonencoder) |

## Dependency decisions

### Accept `swift-argument-parser`

It replaces bespoke `CommandLine.arguments` parsing with typed arguments, options, flags, validation, generated usage/help, subcommands, completion generation, and standardized exit handling. Those are all public responsibilities of the CLI boundary; TripleCore should remain unaware of Argument Parser. The package's own usage guide documents typed property wrappers and `ParsableCommand`, while the standard library's `CommandLine` facility provides only raw arguments. [Argument Parser usage](https://github.com/apple/swift-argument-parser/blob/1.8.2/README.md#usage) · [`CommandLine`](https://developer.apple.com/documentation/swift/commandline)

Use a SwiftPM requirement beginning at `1.8.2` and commit the resolved version. Argument Parser follows semantic versioning and limits source-breaking public API changes to a new major version. Its exact generated help and error wording is explicitly outside that stable API, so test Triple's option structure and exit behavior without making upstream prose a permanent Triple contract. [Argument Parser project status](https://github.com/apple/swift-argument-parser/blob/1.8.2/README.md#project-status)

### Do not add `swift-log`

SwiftLog 1.14.0 is current and maintained, but it is an API facade whose production behavior requires choosing a logging backend. Triple is macOS-only and has direct access to Apple's unified `Logger`; user-facing progress and build output are presentation streams, not diagnostic logging. Adding SwiftLog would therefore create another abstraction and likely another backend without satisfying the stdout/stderr or JSON contracts. [SwiftLog 1.14.0](https://github.com/apple/swift-log/releases/tag/1.14.0) · [SwiftLog README](https://github.com/apple/swift-log/blob/1.14.0/README.md#available-log-handler-backends) · [Apple `Logger`](https://developer.apple.com/documentation/os/logger)

### Do not add `swift-system`

Swift System 1.7.5 is current and maintained, and its stated scope is idiomatic low-level OS interfaces. TripleCLI needs only standard stream descriptors and `isatty`, both already present in the macOS SDK through Foundation and Darwin. Adopt Swift System later only if a broader, repeated low-level file-descriptor surface emerges; it does not pay for itself for one terminal predicate. [Swift System 1.7.5](https://github.com/apple/swift-system/releases/tag/1.7.5) · [Swift System scope](https://github.com/apple/swift-system/blob/1.7.5/README.md) · [`isatty(3)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/isatty.3.html)

## Contract implications

1. Make the root command an `AsyncParsableCommand`; keep parsing types and all formatting/output routing in `TripleCLI`, while commands call reusable operations in `TripleCore`. [Async command guide](https://github.com/apple/swift-argument-parser/blob/1.8.2/Sources/ArgumentParser/Documentation.docc/Extensions/AsyncParsableCommand.md)
2. Serialize writes through one CLI-owned router so concurrent operation events cannot interleave bytes. Consume existing TripleCore operation snapshots and process events as async sequences rather than adapting them to a logging library. Swift's streams are designed to bridge event producers into `async` iteration and expose cancellation. [`AsyncStream`](https://developer.apple.com/documentation/swift/asyncstream) · [`AsyncIteratorProtocol` cancellation](https://developer.apple.com/documentation/swift/asynciteratorprotocol#Cancellation) · [TripleCore operation snapshots](../../../TripleCore/Sources/TripleCore/Operations/OperationCoordination/OperationCoordinator/OperationCoordinator+Observation.swift) · [TripleCore process events](../../../TripleCore/Sources/TripleCore/Operations/ProcessExecution/ProcessSession.swift)
3. Treat stdout as the result channel. In human mode, stderr carries progress and diagnostics. In JSON mode, stdout contains one JSON document; suppress transient progress and reserve stderr for diagnostics under the eventual output contract.
4. Decide explicitly whether parse/validation failures under `--json` must also be JSON. Argument Parser's default entry point prints clean exits to stdout and failures to stderr; if the JSON contract includes parser failures, use its public parse/message/exit-code APIs from a custom async entry point instead of relying on default `@main` error presentation. [Argument Parser exit implementation](https://github.com/apple/swift-argument-parser/blob/1.8.2/Sources/ArgumentParser/Parsable%20Types/ParsableArguments.swift#L199-L225)
5. Generate completions from the command tree. Do not install them silently; Argument Parser documents different user-controlled locations for Zsh, Bash, and Fish. [Completion installation guide](https://github.com/apple/swift-argument-parser/blob/1.8.2/Sources/ArgumentParser/Documentation.docc/Articles/InstallingCompletionScripts.md)

## Bottom line

The smallest justified foundation is **one package: `swift-argument-parser` 1.8.2**. Swift 6.3 concurrency plus the macOS 26 SDK already cover every other identified concern. Keep the output router and versioned JSON schema owned by TripleCLI; neither belongs in a generic logging or terminal framework.
